# 投稿をメインにしてCanvasも更新する（v0.5.0）

## 動作

```text
本文：#制作物-イラスト ＋ 画像・リンク
        ↓ 週1回
チャンネル：今週の制作物
  └─ スレッドに分類別の一覧
        ↓ 同じ実行で、同じ一覧
Canvas：週ごとの見出しの下へ追記
```

処理順は、親投稿 → 分類別のスレッド一覧 → Canvas末尾への追記 → 親投稿のピン留めです。
画像実体をコピーせず、ファイル名と元投稿リンクを両方に掲載します。Canvasの既存内容は残します。
制作物の投稿・まとめ投稿・Canvasを同じチャンネルで運用できます。

## 設定

1. 起動中のボットを停止し、今回のコードへ更新します。既存の `.env` と `.state` を引き継ぎます。
2. コードのフォルダで `npm ci --ignore-scripts` を実行します。
3. Bot Token Scopesを確認して、権限を追加した場合はSlackアプリを再インストールします。

| 権限 | 用途 |
|---|---|
| `channels:history` | パブリックの収集元の履歴取得 |
| `chat:write` | 親投稿とスレッド一覧の投稿 |
| `canvases:write` | Canvas作成・追記 |
| `pins:write` | 自動ピン留めを使う場合 |
| `app_mentions:read` | 参加者のメンションによる曜日・時刻変更を使う場合 |

収集元がプライベートなら `channels:history` を `groups:history` に変更します。
Socket Modeのアプリレベルトークンには引き続き `connections:write` が必要です。
更新した `slack-manifest.json` は「投稿＋Canvas」用の権限を含みます。`slack-manifest-canvas.json` はCanvasだけの別構成用なので、今回の申請では前者を使ってください。

`.env` は次のように設定します。トークンとチャンネルIDは従来のものを引き継ぎます。

```dotenv
OUTPUT_MODE=both
ALLOW_SLACK_POST=true
ENABLE_WEEKLY=false
AUTO_PIN=true

SLACK_CANVAS_ID=F実際の本番CanvasID
SLACK_TEST_CANVAS_ID=F実際のテストCanvasID
```

練習では2つのCanvas IDを同じにして試せます。Canvas未作成の場合は [CANVAS.md](CANVAS.md) に従い `npm run canvas:setup` で作成します。テスト時に本番Canvasへの自動切り替えはしません。

## 手動テスト

先にチャンネル本体へ架空の制作物を投稿します。

```text
#制作物-イラスト
動作確認です。
［画像を添付］
```

```bash
npm run preview
npm run post:test -- --run-id=3
```

番号3は例です。その日にまだ使っていない番号を使います。同じ日・同じ番号は重複防止で停止します。
チャンネルの親投稿・分類別スレッド、Canvasの同じ期間の分類別一覧、親投稿のピンを確認します。
テスト中は `ENABLE_WEEKLY=false` で構いません。

## 週次運用

動作確認と学校の承認後、`ENABLE_WEEKLY=true` にして `npm start` を実行します。
初期設定は月曜9時（日本時間）です。チャンネル参加者は [SCHEDULE.md](SCHEDULE.md) のメンション操作で曜日・時刻を変更できます。集計は引き続き前週分です。稼働環境の停止・スリープ中は実行できません。
0件の週はチャンネル投稿もCanvas追記も行いません。

## エラー時の動作

| 状態 | 同じコマンドを再実行した場合 |
|---|---|
| 両方とも成功 | 再投稿・再追記せず `already_processed` |
| チャンネル投稿が途中・結果不明 | 担当者の確認まで停止。Canvasにも進まない |
| 投稿成功、Canvasは権限不足などで明確に拒否 | 権限修正後にCanvasだけを再試行し、最後にピン留め |
| 投稿成功、Canvasの通信結果不明 | 成功済みの可能性があるため再送しない。担当者がCanvasを確認 |
| 両方成功、ピン留めだけ失敗 | 投稿・Canvasを繰り返さずピン留めのみ再試行 |

Canvasだけを再試行するときは、元の実行期間を使って履歴を取り直します。投稿後に本文・添付・分類設定が変わっていれば、チャンネルと異なる内容を追記しないよう停止します。Canvas IDの変更や記録の不整合がある場合も停止します。
通信結果不明時、元投稿の変更後、設定変更時の復旧はREADMEの担当者向け手順に従い、Slack側の状態を確認してから行ってください。週次運用で新しいテスト番号を使って復旧することはできません。

## 旧版からの切り替え

- 同じ期間・番号のスレッド投稿が既に完了している場合、新しいチャンネル投稿は作りません。旧版でCanvas同期を記録していないものへ、自動で後付け追記もしません。テストは別番号、週次は次の未処理週で確認してください。
- 同じ期間・番号を既にCanvasだけに追記済みの場合、既存のCanvas記録を再利用し、チャンネル側だけを投稿します。Canvasの古い内容は書き換えません。
- 途中失敗した旧版の記録がある場合は、担当者が状態を確認してから切り替えます。

## ローカルの保存情報

`.state/ledger.json` に、処理期間・チャンネルID・親投稿ID・Canvas ID・処理状態・件数・内容照合用のSHA-256ハッシュを保存します。
本文、画像実体、ファイル名、生成した一覧本文、プロフィールはディスクに保存しません。失敗からの再開時にハッシュを比較し、同じ内容であることを確認します。
実行記録を削除したり別環境で別の記録を使うと重複を防げません。1つの稼働環境・単一プロセスで運用してください。

## GitHub提出用の説明文

> Bolt for JavaScriptで稼働する制作物週次まとめボットです。指定チャンネルの「#制作物」または「#制作物-分類名」付き投稿を抽出し、週1回、チャンネルに親投稿と分類別のスレッド一覧を投稿します。同じ実行で同じ一覧をSlack Canvasの末尾に追記し、過去分を残します。
>
> 処理は学校が承認したボット稼働環境で実施します。画像・添付本体のダウンロードや外部サービスへの転送は行わず、ファイル名とSlack元投稿へのリンクを掲載します。投稿本文やAPI応答の付随情報は判定のため一時的に取得しますが、本文・ファイル名・プロフィールは永続保存しません。
>
> 必要なBotスコープは channels:history（プライベートならgroups:history）、chat:write、canvases:write、および自動ピン留め用のpins:writeです。アプリレベルトークンにconnections:writeを使用します。コード・権限・データの取り扱い・稼働環境について審査をお願いします。

申請時にメンションによる予定変更も含める場合は、SCHEDULE.mdの追加説明（チャンネル参加者全員による操作、app_mentionの購読、予定・イベント識別子の保存）も提出してください。
