# データの取り扱い・審査向け説明

## アーキテクチャ

```text
Slackの指定チャンネル
    ↓ HTTPS / 履歴を期間指定で取得
学校承認のNode.js稼働環境（Bolt）
    ・メモリで #制作物 を判定
    ・添付メタデータのファイル名と元投稿リンクで一覧を作成
    ・画像本体を取得しない
    ↓ HTTPS / 親投稿・返信・ピン留め
同じワークスペースの指定チャンネル
```

常駐時はSocket ModeでSlackへ接続します。公開HTTPサーバーやOAuthの公開コールバックは用意しません。制作物は週次の履歴取得で抽出します。メンション管理を使う場合はapp_mentionイベントのみ購読します。

v0.3では `#制作物-イラスト` 等の本文タグで分類します。ショートカット・モーダル・`commands` 権限・`views.open` は使用しません。

## 接続先

- アプリによるAPI通信先はSlack公式APIです。Socket ModeはSlackが返すWebSocket接続先を使用します。
- Googleサービス・GitHub・外部AI・投稿内URLへ投稿データを送信するコードはありません。
- GitHubはコードの配布先です。依存パッケージのインストール時はnpmレジストリへ接続します。
- OS、ネットワーク、実行環境のバックアップ・監視・プロキシ等は学校の管理対象であり、このコードだけで管理できる範囲には含みません。

## 取得する情報と保持

| 情報 | 取得・保持 |
|---|---|
| 指定期間の投稿本文 | 判定のためメモリで取得。本文のディスク保存・ログ出力なし |
| 投稿者ID等のAPI付随情報 | API応答に含まれ得る。プロフィールの追加取得・永続保存なし |
| ファイル名 | API応答で取得可能なものをメモリで使用し、Slackの一覧へ掲載 |
| 画像・添付の実体 | 取得しない |
| 元投稿URL | Slackの一覧へ掲載。外部サイトへアクセスしない |
| 実行記録 | 対象期間、投稿先ID、親投稿ID、状態、返信数をローカル保存 |
| 認証情報 | 環境変数／稼働環境の.envで管理 |

プレビューでも実データの読み取りは行います。目印以外の投稿や個人識別情報がメモリに入る可能性を排除できません。ファイル名に個人情報があればまとめにも含まれます。これらは学校の審査・運用ルールで許可範囲を確認する必要があります。

## 対策

- 初期状態は投稿と自動実行を無効化。架空データのmockは通信なし。
- 入力は設定済みの収集元1チャンネルに限定。投稿先も設定済みIDのみ。
- ファイルダウンロードAPI・ユーザープロフィールAPI・外部URLアクセスを実装しない。
- 元投稿リンクはhttpsのSlackドメインであることを検証。
- ファイル名のメンション・書式の埋め込みを無害化。リンクプレビューを無効化。
- 例外オブジェクト・API応答・イベント・投稿本文・ファイル名・トークンをログへ出さない。
- 状態ディレクトリは所有者限定、状態ファイルは所有者読み書き権限（POSIX環境）。Windowsでは管理者がACLを設定する。
- ローカルロック・投稿前の実行記録で重複を抑止。状態消失時や別環境との重複は保証対象外。
- 結果不明な投稿の自動再送はしない。ピン留めだけの失敗では本文を再投稿しない。
- 依存バージョンをpackage-lock.jsonに固定し、インストール時のライフサイクルスクリプトを無効化する手順を採用。
- 分類は管理者が設定した候補との一致で判定し、候補外・未指定は「制作物」にする。分類を別途ローカル保存せず、旧版の分類状態ファイルも参照しない。

## 管理者の作業

- 稼働環境とチャンネルの公開範囲を承認し、トークン・コード編集権限を管理する。
- コード／依存関係の変更時に再確認する。依存監査結果は時点で変わる。
- 漏えいが疑われる場合はプロセスを止め、Slack側で該当トークンを失効・再発行する。
- 制作物の機密情報・個人情報、元投稿削除時のまとめの修正、過去のピン整理を管理する。
- 状態ファイルやサーバーバックアップも学校のルールに沿って管理する。

本資料は設計とコードの説明であり、学校の審査承認や個人情報非取得を保証するものではありません。

## Canvasモード（v0.4.0）

- `OUTPUT_MODE=canvas` の場合、指定した1枚のCanvasへ期間・分類・元投稿リンクを追記します。外部サービスへの転送は追加しません。
- 必要な追加スコープは `canvases:write` です。このスコープ自体には削除権限も含まれますが、実装は `canvases.edit` の `insert_at_end` と、明示コマンドによる `conversations.canvases.create` に限定します。
- 既存Canvas本文を取得・保存せず、置換・削除を行いません。画像実体は取得しません。
- 実行記録にはCanvas IDと対象期間・状態等の識別情報のみを保存します。Canvas本文や生成したMarkdownのディスク保存・ログ出力は行いません。
- Canvas向けにファイル名のMarkdownをエスケープし、リンク先をSlackのHTTPS URLに限定します。Chat APIのプレビュー無効化オプションはCanvasにはありません。外部URLを埋め込むコードはなく、Slack元投稿への通常リンクを使います。
- Canvasの閲覧者・編集者と稼働環境を学校が確認してください。既存の独立Canvasを指定した場合、チャンネルの権限を自動継承するとは仮定しません。
- チャンネルCanvasのアクセスはチャンネルに対応します。Canvasの利用可否と作成・編集権限は学校の管理設定・契約によります。
- 通信結果不明時に自動再送しない設計です。状態ファイルを失った場合、二重追記は防げません。

## 投稿＋Canvasの併用（v0.5.0）

- チャンネル投稿とスレッド一覧を作成し、その後に同じ一覧をCanvasへ末尾追記します。`chat:write` と `canvases:write` の両方が必要です。自動ピン留めは `pins:write` を使います。
- 実行記録に対象期間・チャンネルID・親投稿ID・Canvas ID・処理状態・件数・整合性確認用のSHA-256ハッシュを保存します。一覧本文やファイル名そのものは保存しません。
- 投稿完了後、Canvasが権限不足等で明確に拒否された場合はCanvasのみ再試行できます。履歴を再取得し、ハッシュが一致する場合だけ追記します。
- Canvasの通信結果が不明な場合、チャンネル投稿が途中の場合、内容や設定が変わった場合は自動再送せず確認を待ちます。ピン留めだけの失敗ではピンのみ再試行します。
- 二つのSlack書き込みを一つの原子的な操作にはできないため、一方だけ完了する状態はあり得ます。ログと実行記録で区別して復旧し、完了済みの書き込みを繰り返さない設計です。

## メンションによる予定変更（v0.6.1）

- 追加スコープはapp_mentions:read、追加イベントはapp_mentionです。指定した収集元チャンネルに投稿できる参加者全員の操作を受け付けます。
- 個人IDの登録・許可リストは使用しません。一般利用者のプロフィールを追加取得しません。イベントの利用者IDはSlackが提供するイベント情報としてメモリで扱いますが、保存・ログ出力しません。
- `.state/schedule.json` に曜日・時刻・適用開始時刻・直近100件のイベント識別子を保存します。指示本文や操作利用者IDはこのファイルやログへ保存しません。
- 指示は定型パーサーで処理し、コードやシェルを実行せず、外部AIへ送信しません。他チャンネル・ボット・利用者不明・古い指示は無視します。
- 週次実行そのものの有効化、出力先・権限・稼働環境の変更はメンションでは行いません。学校の運用担当者が稼働環境で設定します。
- 同じイベントの再配信を抑止し、曜日を変更しても同じ週の完了済みまとめは再投稿しません。投稿本文やCanvasに対するデータ保護の範囲は従来どおりです。
- 指定チャンネルの参加者全員が予定を変更できる運用であることを、学校の審査資料に明記してください。利用者が卒業しても、操作権限の個人ID入れ替えは不要です。
