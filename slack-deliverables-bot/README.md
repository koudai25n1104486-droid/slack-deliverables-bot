# 制作物・週次まとめボット（Bolt）

**v0.7.0：好きな時に `@ボット 今週の制作物` と指示して、その時点までの一覧を見られます。** 使い方は **[REPORT.md](REPORT.md)** を参照してください。

**v0.6.1：指定チャンネルの参加者なら、誰でもメンションで投稿曜日・時刻を変更できます。個人IDの登録・卒業時の入れ替えは不要です。** `@ボット 毎週 金曜 18:00` の形式です。追加設定と練習方法は **[SCHEDULE.md](SCHEDULE.md)** を参照してください。

**v0.5.0：チャンネル投稿をメインにして、同じ一覧をCanvasにも追記できます。** 推奨設定は `OUTPUT_MODE=both` です。**[投稿＋Canvasの設定手順](BOTH.md)** を参照してください。Canvas自体の準備は [CANVAS.md](CANVAS.md) に記載しています。

指定したSlackチャンネルの本文に **`#制作物`** が付いた投稿を読み、ファイル名と元投稿へのリンクを週次スレッドに投稿し、同じ一覧を1枚のCanvasにも追記できます。GAS・Google Sheets・Google Drive・外部AIは使いません。

**v0.3.0：本文のタグだけで分類できます。** 例：`#制作物-イラスト`。メニュー操作や分類用の追加権限は不要です。未指定・候補外は「制作物」にまとめます。更新方法は **[タグ分類版への更新手順](UPGRADE-v0.3.md)** を参照してください。

```text
今週の制作物
対象期間：前週月曜0時〜今週月曜0時（日本時間）
└─ スレッド
    イラスト
      • のーたんさん20261114.png → 元投稿
    制作物
      • ぴんちゃんさん20261111.jpeg → 元投稿
```

画像本体は元投稿で閲覧します。画像をダウンロード・再アップロードするコードはありません。ファイル名が取得できないときは「添付ファイル（日付）」、添付のない投稿は「制作物（日付）」で表示します。プロフィールから投稿者名を追加する処理はありません。

## 実行環境

- 学校が承認したPC／サーバー上の **Node.js 22.9以降**。承認されたサポート中のLTS版を使用してください。
- フレームワークは **Bolt for JavaScriptのみ**。直接の実行依存は `@slack/bolt` 4.7.3です。
- 時刻確認・設定ファイル読み込み・状態保存・テストにはNode.js標準機能を使います。
- 常駐起動中はBoltのSocket Modeを使います。公開HTTP受信口は設けません。
- 学校の許可を受けた環境・テストデータで接続してください。ローカル実行も稼働環境としての確認対象です。

## 分類の書き方

半角の `#` と `-` を使い、タグは単独の行にしてください。

```text
#制作物-イラスト
新しいイラストです。
［画像を添付］
```

| 投稿のタグ | まとめの見出し |
|---|---|
| `#制作物-イラスト` | イラスト |
| `#制作物-動画` | 動画 |
| `#制作物-文章` | 文章 |
| `#制作物-音楽` | 音楽 |
| `#制作物-その他` | その他 |
| `#制作物`、`#制作物-未知の分類` | 制作物 |

候補はコード直下の `categories.json` で変更し、変更後はボットを再起動します。空白を含む分類名は使えません。複数の対象タグがある場合は先頭のタグを採用します。タグは投稿ごとの分類なので、同じ投稿の添付には同じ分類が付きます。

## 1. 架空データで確認する

このフォルダに移動して実行します。モック表示にはトークンも依存パッケージのインストールも不要です。

```bash
npm run mock
```

架空のツリーがターミナルに表示されます。Slackへの接続・投稿は行いません。

## 2. 依存パッケージをインストールする

```bash
npm ci --ignore-scripts
```

`package-lock.json` に固定した依存関係を使います。インストール時はnpmレジストリへの通信が必要ですが、Slackの投稿内容は送信しません。Bolt内部の依存パッケージも審査対象としてロックファイルから確認できます。

## 3. Slackアプリを設定する

既存の「制作物さん」を使う場合は、下記の権限と接続設定に合わせてください。新しく作る場合は `slack-manifest.json` をアプリ作成時のマニフェストとして使えます。

### Bot Token Scopes

| 権限 | 用途 |
|---|---|
| `channels:history` | パブリックの収集元チャンネルの履歴取得 |
| `chat:write` | 親メッセージと返信の投稿 |
| `pins:write` | 親メッセージのピン留め |
| `canvases:write` | both / canvasモードでのCanvas作成・追記 |
| `app_mentions:read` | 参加者のメンションによる予定変更・随時集計を使う場合 |

収集元がプライベートの場合は `channels:history` の代わりに `groups:history` を使います。両方が必要な運用でなければ同時に要求しません。`AUTO_PIN=false` にする場合は `pins:write` を外せます。

`files:read` と `users:read` は要求しません。メンション管理を使う場合は `app_mentions:read` を追加します。添付情報が制限されてファイル名が取得できない場合は元投稿リンクで代替します。実際のファイル名の取得可否はテストチャンネルで確認してください。

### 接続

1. **Socket Mode** をオンにします。
2. **Basic Information → App-Level Tokens** で `connections:write` を付けた `xapp-` トークンを作成します。
3. 権限変更後はワークスペースへ再インストールし、`xoxb-` トークンを確認します。
4. 収集元・テスト投稿先・本番投稿先へボットを追加します。
5. **メンション管理を使う場合だけ** Event Subscriptionsをオンにし、Bot Eventsに `app_mention` を追加します。`message.channels` 等の通常投稿のイベント購読は不要です。制作物は週次の履歴取得で抽出します。

同じボットの古いNode.jsプログラムが動いている場合は停止します。古いGAS版の定期処理も別途停止してください。このコードを作成しても既存の自動処理は停止しません。

タグ分類にはショートカット・Interactivity・`commands` の追加設定は不要です。旧版で追加したショートカットは使用しません。

審査用には、このマニフェストで新しいアプリを作成すると権限を確認しやすくなります。既存アプリの設定から不要なスコープを削除しても、発行済みトークンの権限が直ちに消えるとは限りません。既存アプリを使う場合は管理者が旧トークンの失効・必要に応じた再インストールを含め、実際の許可権限を確認してください。

## 4. `.env` を設定する

```bash
cp .env.example .env
chmod 600 .env
```

Windowsではファイルのコピーとアクセス制限をOSの機能で行ってください。

`.env` に値を設定します。以前の `.env` にあるトークンを再利用できますが、チャンネルの項目名は今回のコードに合わせます。トークンをREADME・チャット・GitHubに貼り付けないでください。

```dotenv
SLACK_BOT_TOKEN=xoxb-実際のボットトークン
SLACK_APP_TOKEN=xapp-実際のアプリトークン
SLACK_SOURCE_CHANNEL_ID=C0123456789
SLACK_TEST_CHANNEL_ID=C1123456789
SLACK_OUTPUT_CHANNEL_ID=C2123456789
ALLOW_SLACK_POST=false
ENABLE_WEEKLY=false
AUTO_PIN=true
OUTPUT_MODE=both
SLACK_CANVAS_ID=F実際の本番CanvasID
SLACK_TEST_CANVAS_ID=F実際のテストCanvasID
MAX_ITEMS=50
MAX_PAGES=20
```

- `SLACK_SOURCE_CHANNEL_ID`：収集元のチャンネルID
- `SLACK_TEST_CHANNEL_ID`：テスト結果を投稿するチャンネルID
- `SLACK_OUTPUT_CHANNEL_ID`：本番の週次まとめを投稿するチャンネルID
- テスト先と本番先は分けてください。各チャンネルの所属ワークスペースと参加者は学校が確認します。
- `.env` はNode.js標準機能で読みます。dotenv等の追加ライブラリは不要です。

## 5. 読み取りだけで確認する

収集元チャンネルの本体に、架空の制作物を投稿します。`#制作物` は単独の行にしてください。スレッド返信は対象外です。

```text
#制作物
動作確認用の画像です。
［架空の画像ファイルを添付］
```

```bash
npm run preview
```

直近7日間の「取得数・対象投稿数・一覧項目数」を表示します。本文・ファイル名をログに出さず、Slackへの投稿や状態ファイルの作成もしません。

## 6. 手動でテスト投稿する

`.env` の `ALLOW_SLACK_POST=true` に変更して実行します。

```bash
npm run post:test
```

直近7日間（実行時刻まで）を対象に、テスト先へ親メッセージ・分類ごとの一覧返信を投稿し、親メッセージをピン留めします。長い一覧は分割します。リンクプレビューは無効です。

- 番号未指定のテストは、同じ日本時間の日付・同じテスト先で1回だけ投稿します。
- 0件の場合も、その日の処理済み記録を残します。テスト投稿はコマンド実行前に用意してください。
- もう一度テストする場合は `npm run post:test -- --run-id=2` を使います。さらに試すときは3、4と番号を変えます。同じ日・同じ先・同じ番号は重複防止します。以前のまとめは残ります。番号は手動テスト専用で、週次実行では使えません。
- このボットはSlackのメンションには返信しません。テストの開始はターミナルから行います。

## 7. 週次実行

審査とテストが完了したら `.env` を設定します。

```dotenv
ALLOW_SLACK_POST=true
ENABLE_WEEKLY=true
```

```bash
npm start
```

初期設定では毎週月曜9時以降に、**前週月曜0時〜今週月曜0時**の投稿をまとめます。曜日・時刻は参加者のメンションで変更できますが、集計期間は変わりません。判定は日本時間です。Node.js標準タイマーで1分ごとに実行時刻を確認します。

- プロセスが動いている間だけ実行します。PCのスリープ・終了中は実行できません。
- 保存した予定時刻より後に起動した場合、その週の前週分を未処理なら実行します。メンションで変更した設定は次の予定から適用します。
- 長期間停止した場合に、過去の未処理週をすべてさかのぼる処理はありません。
- 0件の週は投稿しません。実行記録で同じ期間の処理を抑止します。
- 停止は **Control＋C** またはサーバー管理者によるプロセス停止です。進行中の処理がある場合は完了まで待ちます。
- ピン数には上限があるため、過去のピンは担当者が整理してください。

分類の読み取りだけを練習する場合は `npm run preview` を使います。`ENABLE_WEEKLY=false` のままで実行でき、結果には分類ごとの件数が表示されます。`npm start` は週次運用を有効にした場合だけ常駐します。

前週分を手動で本番先に投稿する場合は、明示的に次を実行します。`ENABLE_WEEKLY` がfalseでも `ALLOW_SLACK_POST=true` なら実行されます。

```bash
npm run post:weekly
```

## 8. 障害・重複防止・再テスト

`.state/ledger.json` に、対象期間・投稿先ID・親メッセージIDまたはCanvas ID・処理状態・返信完了数などを保存します。投稿とCanvasを併用する場合は内容照合用のハッシュも保存します。本文・ファイル名・プロフィール・トークンは保存しません。直近128回分を保持します。

- 投稿前に記録を作成し、途中失敗・通信結果不明時には再投稿を止めます。
- 投稿APIの自動リトライは無効です。結果不明の二重投稿を避けるため、確実な障害復旧を優先します。
- ピン留めだけに失敗した場合は、同じコマンドでピン留めのみを再試行します。親・返信は再投稿しません。
- 取得に失敗した場合や件数上限を超えた場合は、親メッセージを作りません。
- 常駐中のエラー後の再確認は最短1時間後です。途中投稿の記録がある場合は再投稿せず担当者の確認を待ちます。

### 再テストや途中投稿の復旧

1. ボットを停止します。同じ状態ディレクトリを使う別プロセスがないことを確認します。
2. Slack側で不完全な親メッセージ・返信の有無を確認し、必要に応じて手動で削除します。
3. `.state/ledger.json` の `records` 配列から、**該当するテスト日／週と投稿先のレコードだけ**を削除します。ファイル全体を削除すると本番の処理済み記録も失われます。
4. 強制終了等で `.state/run.lock` が残っている場合だけ、実行プロセスがないことを確認してこのファイルを削除します。
5. コマンドを再実行します。

状態ファイルを失った場合や複数サーバーで別々の状態ファイルを使う場合は、重複防止は機能しません。**単一の稼働環境・単一プロセス**で運用してください。

分類は本文のタグから毎回判定し、分類専用の状態ファイルは作りません。旧版の `.state/categories.json` は参照しません。週次まとめの重複防止用 `.state/ledger.json` は引き続き使用します。

## 9. 学校への審査資料

詳細は `SECURITY.md` を参照してください。

- Slack APIからの応答を稼働環境のメモリで処理します。厳密な「Slackサーバーだけで処理」ではなく、学校が許可したボット稼働環境で処理する構成です。
- 目印のない投稿も抽出のために読みます。API応答に投稿者ID等が含まれることがあるため、「個人情報を一切取得しない」とは保証しません。
- ファイル名に個人情報があると、まとめにも掲載されます。架空データでテストし、掲載ルールを学校と確認してください。
- 収集元の閲覧権限は反映先へ自動継承されません。ファイル名だけでも情報になるため、反映先の共有範囲を確認してください。
- 元投稿の編集・削除はまとめへ同期しません。Slackの保存期間によりリンクが閲覧できなくなることがあります。
- 分類は同じ投稿の添付全体に適用します。分類を変えても投稿済みのまとめは変更しません。

## 10. 検証とGitHub登録

```bash
npm run check
npm test
npm audit --omit=dev
```

テストは架空データのみを使い、Slackへ通信・投稿しません。日付の境界、収集条件、表示の無害化、重複防止、途中失敗、ピン留め再試行、ローカルロック、タグ分類・候補外の扱い・旧分類ファイルを参照しないことを確認します。

GitHubに登録するのは、このフォルダのコード・ドキュメント・マニフェスト・ロックファイル・設定例です。`.env`、`.state/`、`node_modules/`、ログは登録しません。`.gitignore` に除外を設定済みです。リポジトリはまだGitHubへ公開していません。

実際のSlack接続・投稿・ワークスペースごとのファイル名取得可否は、学校が承認したテスト環境で別途確認が必要です。

## 出力先の選択

| OUTPUT_MODE | 動作 |
|---|---|
| both | チャンネル投稿＋スレッド一覧を作成し、同じ一覧をCanvasへ追記（今回の推奨） |
| thread | チャンネル投稿＋スレッド一覧のみ |
| canvas | Canvasへの追記のみ |

設定例の初期値はbothですが、互換性のためOUTPUT_MODE自体が未設定の場合はthreadです。Canvas IDをまだ用意していない段階ではthreadでテストできます。bothは [BOTH.md](BOTH.md) の部分失敗時の動作も確認してください。

スケジュール設定とメンション操作の保存情報・チャンネル参加者の操作範囲は [SCHEDULE.md](SCHEDULE.md) を参照してください。
